## Root cause

`assets/recipes/chicken.json` and `assets/recipes/pork.json` are single
generic packs (`RecipePackParser`) whose injected hero `RecipeIngredient`
always uses the pack's one literal id (`"chicken"` / `"pork"`), and neither
pack declares ANY compatibility metadata (`exactIngredientIds`,
`preferredIngredientIds`, `compatibleIngredientIds`, `substituteIngredientIds`,
`ingredientFamilyIds`) anywhere -- confirmed by inspecting the raw JSON: their
only top-level keys are `version`/`hero`/`recipes` (and `defaultPrimaryWeight`
for pork). Compare `assets/recipes/fish.json` and `mackerel.json`, which both
declare pack-level compatibility fields consumed by every recipe in the pack
via `RecipePackParser._compatibilityFor`.

`assets/ingredients/thai_ingredients.json` (plus
`pantry_catalog_canonical_definitions.dart`'s seeds) correctly defines
`chicken_breast`, `chicken_wing`, `chicken_thigh`, `minced_pork`, `pork_belly`,
and `pork_neck` as distinct, selectable canonical ingredients with
`parentId: "chicken"` / `"pork"`.

`MainIngredientCompatibilityService._resolveTier` deliberately does **not**
consult canonical ancestry on its own (`registry.areCompatibleIds` is a
different, ancestor-aware path used only by `RecipeReadinessService` for
pantry *readiness*, not by the hero/compatibility engine). A cut-level
canonical id is only eligible for a recipe if that recipe's own metadata
explicitly lists it (`exactIngredientIds`/etc.) or explicitly opts into a
shared family (`ingredientFamilyIds`) that the ingredient's ancestor chain
also names. Since chicken.json/pork.json declare none of this, every one of
the six named pantry cuts resolves to `MainIngredientExclusionReason.noMatch`
against every chicken/pork recipe -- for all six, unconditionally.

`SmartRecommendationEngine._buildHeroOptions` only creates a hero candidate
for a pantry ingredient when it has *at least one* eligible match. With zero
eligible matches, these six ingredients never become hero candidates -- not
automatically, and (per `_buildCandidateForSelection`) not even if the user
manually selects them. If the pantry's other qualifying ingredients are also
absent right after an update, `automaticCandidates` is empty and
`SmartRecommendation.hero == null` / `primaryMatches == const []` is returned
-- `top_picks_section.dart`'s `if (!rec.hasHero || rec.primaryMatches.isEmpty)
return const SizedBox.shrink();` then hides the hero row entirely. This is
the missing-hero symptom.

**Important nuance proven by this audit's fix-validation test:** merely
adding `ingredientFamilyIds` to chicken.json/pork.json is *not* sufficient by
itself. `SmartRecommendationEngine.build()` explicitly filters
`evaluatedForHero.where((m) => m.mainIngredientMatchTier != family)` when
building `heroPool` (and therefore `primaryMatches`) -- family-tier matches
are demoted to the separate `adaptableMatches` bucket, not the primary hero
carousel. A pantry cut whose only eligible matches are family-tier would
still show `hasHero == true` (it can still win as the *only* candidate) but
`primaryMatches == []` -- Home would still render `SizedBox.shrink()`. The
fix must land these cuts in a tier stronger than `family`
(`compatibleIngredientIds` is the natural, minimal choice) to actually
restore the hero row.

**Real-world corroboration of the family-tier nuance, visible in the
Primary-protein coverage table above:** `sea_bass` and `tilapia` (both
`parentId: "fish"`) already have `familyOnly` matches (11 and 6
respectively, via `fish.json`'s pack-level `ingredientFamilyIds`) yet
`realPathTotal == 0` -- living proof, in production data, that a
family-tier-only match does not surface in Home's `primaryMatches`, exactly
as this audit's synthetic fix-validation test demonstrates for
`chicken_wing`.

**Bonus finding:** `moo_yor` (Vietnamese pork sausage, `parentId: "pork"`)
is affected by the identical root cause and was not in the original bug
report's 6 named ingredients -- see the Summary/NO_MATCH table above.

**Separate, pre-existing data-naming issue (not caused by this bug, not
fixed here):** the canonical id `chicken_thigh` is labeled with the Thai
name "น่องไก่", which conventionally means chicken *drumstick*, not thigh.
There is no distinct `chicken_drumstick` id. Worth a follow-up ticket.

## Did PR #17 cause or merely expose this?

**PR #17 did not cause this.** Its diff (`recipe.dart`,
`resolved_image.dart`, `recipe_image.dart`, `recipe_card.dart`,
`top_picks_section.dart`, `recipe_detail_header.dart`, `pubspec.yaml`,
`thai.json`, `docs/20_IMAGE_FOUNDATION.md`) touched only image
rendering/metadata -- it added `Recipe.image` (an `ImageMetadata?` field with
its own independent precedence over legacy `imageUrl`) and wired
`RecipeCard`/`RecipeDetailHeader` to render photos. It never touched
`MainIngredientCompatibilityService`, `SmartRecommendationEngine`,
`RecipeCandidateService`, `CanonicalIngredientRegistry`, or any
`assets/recipes/*.json` compatibility field.

The root cause predates PR #17 by several commits on `main`
(`12e768e data(recipe): add Thai core ingredient master`,
`f8c3b60 feat(ingredient): add pork neck and beef aliases`,
`95a7521 fix(pantry): cover selectable catalog canonically`,
`f6c0272 fix(pantry): stabilize sprint verification`) -- all of which
predate PR #17's `af55128` merge base. `chicken.json`/`pork.json` have never
declared compatibility metadata since they were introduced.

Test 8 in this suite additionally proves structurally (two otherwise-identical
synthetic recipes, one with approved `ImageMetadata`, one with none) that
image metadata has zero effect on `MainIngredientCompatibilityService`
eligibility or tier -- the two code paths are fully decoupled. PR #17 merely
coincided in time with when this gap was noticed (during Home/RecipeCard
manual UAT), not in code.

## Smallest safe fix proposal

Data-only change, zero production code touched, directly mirroring the
existing `fish.json`/`mackerel.json` precedent:

Add a pack-level `compatibleIngredientIds` array to
`assets/recipes/chicken.json` and `assets/recipes/pork.json`:

```json
// chicken.json (top level, alongside "hero"/"recipes")
"compatibleIngredientIds": ["chicken_breast", "chicken_wing", "chicken_thigh"]

// pork.json (top level, alongside "hero"/"recipes")
"compatibleIngredientIds": ["minced_pork", "pork_belly", "pork_neck", "moo_yor"]
```

`RecipePackParser._compatibilityFor` already merges any pack-level
compatibility key into every recipe in that pack, so this requires no other
changes. `compatible` is a real, non-`family` tier, so these six ingredients
would appear in `primaryMatches`/the Home hero carousel once this lands (see
"Important nuance" above for why `ingredientFamilyIds` alone would not be
enough). This audit's fix-validation test proves this exact mechanism works
via a synthetic recipe, without editing any production asset.

Do not implement this in this branch -- diagnosis and report only, per
instructions.

## Branch D backlog — generic fish form/texture mismatch

Added during `feature/ingredient-taxonomy-content` (Branch B). Distinct from
the REGRESSION-gap table above; recorded here because it's the same kind of
recipe-content/matching gap, not a taxonomy defect.

**Gap**: `assets/recipes/fish.json`'s pack-level compatibility metadata
declares `requiredIngredientForm: "boneless_fillet"` and
`requiredTexture: "firm_white_flesh"`. The canonical `fish` entry
(`assets/ingredients/thai_ingredients.json`) is deliberately authored with
**no** `ingredientForms`/`textures` — it is a pure semantic generic ("any
fish, unspecified"), and claiming a specific fillet form on it would be a
fabricated assumption purely to make an existing recipe-matching test pass.
That fillet-specific data now lives on `fish_fillet` instead, which is
structurally correct but does not satisfy `fish.json`'s requirement for the
literal id `fish`.

**Consequence**: `MainIngredientCompatibilityService.evaluate()` currently
excludes a pantry item of generic `fish` from `fish.json`'s recipes on the
form/texture gate, even though `exactIngredientIds` names `fish` directly.
Verified via `fish_generic_selectable_regression_test.dart`'s
"generic fish carries no fabricated form/texture assumptions" test (registry
content) plus manual evaluation against real loaded recipes — not shipped as
a skipped/asserted-failing test, since the default suite must show 0 skipped.

**Fix options for Branch D** (recipe matching/content correction territory,
not taxonomy):
1. Relax `fish.json`'s pack-level `requiredIngredientForm`/`requiredTexture`
   for the generic-fish case (e.g. only require it for the more specific
   sub-recipes that already carry their own `compatibleIngredientIds`
   overrides), or
2. Add an explicit compatibility-layer rule (in
   `MainIngredientCompatibilityService` or recipe metadata) that treats
   generic `fish` as satisfying `fish.json`'s form/texture gate by design,
   without touching the canonical taxonomy entry.

Do not "fix" this by adding `boneless_fillet`/`firm_white_flesh` back onto
the canonical `fish` entry — that was the exact anti-pattern Branch B's
Product Acceptance review rejected.
